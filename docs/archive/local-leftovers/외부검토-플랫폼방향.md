# 외부 검토: LensGate 플랫폼 방향 (플러그인 전제 재검토)

2026-10-31 · 사용자가 대화에 붙여 준 외부 검토 원문을 그대로 옮긴 파일이다. 결정 사항은 아니다. 채택 범위는 "방식 A"(Worker 구현 유지, 제품 계약만 한 단계 올림)로 정했고, 미정 3건은 본 세션에서 정한다.

---

그렇다면 **‘플러그인’을 제품의 전제로 둘 필요는 없습니다.** 제 앞선 검토도 “외부 코드를 iframe·Worker 안에서 실행한다”는 현재 구현에 다소 묶여 있었습니다. 그 구현은 하나의 선택지이지, LensGate가 반드시 지켜야 할 제품 형태는 아닙니다.

제 추천은 다음입니다.

> **LensGate는 에이전트가 실행되는 범용 AgentOS보다는, 외부 앱·에이전트가 스마트글래스의 감각 정보에 접근하고 결과를 사용자에게 돌려주는 공통 실행·권한 계층으로 가는 편이 좋습니다.**
>
> API로 능력을 제공한다는 구상에는 찬성합니다. 다만 **외부 서비스의 코드까지 우리 안에서 실행해야 한다는 조건은 빼는 것**을 추천합니다.

AWS AgentCore와 비교하면 **전체 AgentCore를 만드는 것보다는 Gateway·Policy·Identity의 역할을 참고하고, 여기에 단말 내부의 감각 처리를 결합하는 방향**입니다.

그리고 첨부한 HTML은 이 방향을 설명하는 출발점으로 쓸 수 있지만, **현재로서는 사용자 플로우보다 ‘특정 구현 방식의 내부 처리 흐름도’에 가깝습니다.** 제품의 책임 범위를 먼저 정하고, 그다음 그림을 맞추는 순서가 적절합니다.

---

## 1. 가장 먼저 분리해야 하는 두 가지 질문

지금 논의에는 다음 두 가지가 섞여 있습니다.

| 질문 | 예시 | 제 추천 |
|---|---|---|
| **외부 서비스의 코드를 어디서 실행할 것인가?** | LensGate 내부 Worker, 개발자 서버, AgentCore 등 | 당장은 개발자가 선택하도록 둠 |
| **그 서비스가 사용자의 감각에 어떻게 접근할 것인가?** | 음식 조각 요청, 상황 이벤트 구독, HUD 출력 요청 | LensGate가 책임짐 |

**서비스를 실행해 주지 않아도 플랫폼이 될 수 있습니다.** 반대로 서비스를 실행해 준다고 해서 그 플랫폼의 차별성이 생기는 것도 아닙니다.

예를 들어 칼로리 기능 개발자가 이미 자신의 서버를 운영한다고 해보겠습니다.

현재 문서의 방식은 대체로 다음입니다.

```text
개발자가 LensGate용 플러그인 코드를 작성
→ LensGate가 내부 Worker에서 실행
→ 가공된 사진을 전달
→ 플러그인이 칼로리 서버 호출
```

제가 추천하는 제품 구조에서는 다음 방식도 허용합니다.

```text
개발자가 기존 칼로리 서비스를 LensGate에 연결
→ 사용자가 해당 서비스의 감각 접근을 허용
→ LensGate가 허용된 사진 또는 정보를 제공
→ 기존 서버가 처리
→ 결과를 LensGate에 반환
→ LensGate가 글래스에 표시
```

**개발자의 서비스가 어디서 돌아가는지보다, 어떤 입력을 받고 어떤 출력을 요청할 수 있는지가 플랫폼의 계약이 되는 것입니다.**

물론 현재 구현처럼 내부 Worker에서 실행하는 방식도 남겨둘 수 있습니다. 다만 그 위치를 **“플랫폼 자체”가 아니라 “플랫폼에 연결하는 한 가지 실행 방식”**으로 내려놓는 것이 좋습니다.

## 2. AgentCore를 참고하는 것은 맞지만, 참고할 부분을 골라야 합니다

AWS 공식 문서상 AgentCore는 단순한 API 발급 서비스가 아닙니다. 에이전트·도구를 호스팅하는 Runtime, 도구·서비스·모델에 대한 접근을 중개하는 Gateway, 인증·자격 증명을 다루는 Identity, 접근 정책을 집행하는 Policy 등이 구분되어 있습니다. [AWS 문서](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)

이를 LensGate에 대응시키면 다음과 같습니다.

| AgentCore의 역할 | LensGate에 대응하는 역할 | 지금 가져올 필요 |
|---|---|---|
| **Runtime**: 에이전트·도구 실행 환경 | 외부 개발자 코드를 배포·실행·종료하는 환경 | **선택적** |
| **Gateway**: 서비스·도구에 대한 공통 접근 지점 | 카메라에서 얻을 수 있는 정보와 출력 기능을 공통 API로 제공 | **핵심** |
| **Policy**: 실행 코드 밖에서 접근 규칙 집행 | 언제, 어떤 영역을, 어느 해상도·빈도로 제공할지 결정 | **핵심** |
| **Identity**: 호출자 인증·권한 위임 | 어떤 서비스가 어느 사용자의 어느 기기 세션에 접근하는지 확인 | **핵심이지만 범용 인증 시스템을 직접 만들 필요는 없음** |

여기서 가장 배울 만한 원칙은 **“에이전트 자신의 판단과, 그 에이전트가 할 수 있는 일을 제한하는 정책을 분리한다”**는 것입니다. AgentCore Policy도 정책을 에이전트 코드 바깥에서 평가·집행하는 구조를 설명합니다. [AWS 문서](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html)

LensGate에 적용하면 다음과 같습니다.

> 에이전트가 “지금 전체 화면이 필요하다”고 판단할 수는 있다.  
> 하지만 **실제로 전체 화면을 줄지 결정하는 주체는 에이전트가 아니라 LensGate의 권한 정책**이다.

따라서 사용자님이 말한 “우리 서비스에서 API를 할당한다”는 방향은 좋습니다. 다만 더 정확히는 다음에 가깝습니다.

> **서비스에 API 키 하나를 주는 것이 아니라, 특정 사용자의 특정 감각 세션에 대한 제한된 사용권을 부여한다.**

개발자 API 키가 있다고 해서 모든 사용자의 카메라를 볼 수 있어서는 안 됩니다. 개발자 인증, 사용자의 연결 승인, 현재 기기 세션의 활성 상태, 실제 요청의 권한 검사는 별개로 다뤄야 합니다.

## 3. 제가 추천하는 제품: ‘앱·에이전트용 감각 런타임’

제품 설명은 이렇게 잡겠습니다.

> **LensGate는 스마트글래스의 시각 정보를 외부 앱·에이전트가 사용할 수 있도록 제공하되, 접근 범위·처리 방식·전달 대상과 사용자 출력까지 중개하는 감각 런타임이다.**

여기서 중요한 단어는 **‘에이전트용’이지 ‘에이전트만을 위한’이 아닙니다.**

칼로리 조회처럼 단순한 함수도 연결할 수 있고, 여러 단계로 추론하는 에이전트도 연결할 수 있어야 합니다. 모든 기능을 에이전트라고 부르거나, 에이전트 프레임워크를 반드시 쓰게 할 이유는 없습니다.

### 구조는 이렇게 나누는 것이 적합합니다

```text
[스마트글래스 / 데모용 카메라]
                │
                ▼
[사용자 단말의 LensGate 런타임]
  입력 연결
  상황 판정
  권한·빈도·세션 검사
  영역 선택·가림·정보 추출
  전달 기록
                │
        허용된 정보만
                ▼
[연결된 서비스]
  내부 Worker
  개발자의 기존 서버
  외부 에이전트 실행 환경
                │
          결과·출력 요청
                ▼
[LensGate 출력 중개]
  허용된 형식의 카드·음성
  표시 우선순위·유효시간
  사용자의 중단·해제
```

이때 **API를 제공한다는 것이 모든 처리를 클라우드로 옮긴다는 뜻은 아닙니다.**

원본 영상의 보호가 핵심이라면, 원본을 받아 영역을 선택하고 가리는 부분은 사용자의 단말에 있어야 합니다. 원격 서비스와 연결하는 서버가 필요하더라도, 그 서버로 올라가는 것은 정책을 통과한 정보여야 합니다.

실제 Meta 연동에서는 네이티브 모바일 앱을 확장하는 Device Access Toolkit과 글래스에서 실행되는 Web Apps가 별도 개발 경로입니다. 따라서 브라우저 데모의 API를 만들었다는 사실만으로 실제 글래스 연결까지 해결됐다고 볼 수는 없습니다. 실제 기기 입력 어댑터는 별도로 검증해야 합니다. [Meta for Developers](https://developers.meta.com/wearables/faq/)

### API의 단위도 ‘카메라’보다 ‘허용된 관찰’이 좋습니다

플랫폼 API가 다음처럼 생기면 거의 원본 카메라 SDK를 다시 감싼 것에 그칩니다.

```text
카메라 켜기
전체 프레임 받기
사진 저장하기
```

대신 제가 제안하는 능력의 단위는 다음입니다. **아래는 설계 예시이지 현재 구현된 API가 아닙니다.**

| 능력 | 외부 서비스가 받거나 요청하는 것 |
|---|---|
| 상황 이벤트 구독 | “음식으로 판정된 대상이 안정적으로 나타났다”는 이벤트 |
| 관찰 요청 | 현재 허용된 음식 영역 이미지 한 장 또는 구조화된 정보 |
| 결과 제시 요청 | 글래스에 짧은 결과 카드나 음성을 표시해 달라는 요청 |

예를 들어 칼로리 서비스의 허용 범위는 다음과 같이 표현할 수 있습니다.

> 활성화된 사용자 세션에서 음식 영역 한 장을 받는다.  
> 최대 긴 변 256px, 분당 최대 6회, 지정된 수신처만 허용한다.  
> 전체 프레임과 얼굴 원본은 요청할 수 없다.  
> 결과는 짧은 카드로만 제시한다.

**“필요한 정보를 요청한다”와 “받을 정보를 마음대로 지정한다”는 다릅니다.** 요청자가 임의의 좌표를 계속 바꿔 작은 조각을 받으면, 여러 조각을 합쳐 넓은 화면을 복원할 수도 있습니다. 따라서 대상 영역·반복 요청·세션 누적 예산을 함께 제한하는 설계를 권합니다.

또한 텍스트나 객체 목록이라고 무조건 안전한 것도 아닙니다. 원본 이미지 없이도 OCR 결과나 상황 정보에 민감한 내용이 들어갈 수 있으므로, 이미지와 마찬가지로 권한 대상이어야 합니다.

## 4. 어디까지 플랫폼에서 만들어야 하는가?

제 기준은 간단합니다.

> **감각을 안전하게 공유하는 데 필요한 공통 동작은 LensGate가 맡고, 그 감각으로 무엇을 판단하고 어떤 업무를 수행할지는 연결된 서비스가 맡습니다.**

| 영역 | LensGate의 책임 | 외부 서비스의 책임 |
|---|---|---|
| **기기 연결** | 입력 어댑터, 연결 상태, 사용 가능한 능력 확인 | 기기별 연결 코드를 반복해서 작성하지 않음 |
| **감각 접근** | 세션·권한·빈도·영역·해상도 검사 | 필요한 능력과 목적을 요청 |
| **공통 전처리** | 포착, 자르기, 정책에 따른 가림, 기본 상황 판정 | 음식·정비·학습 등 업무별 해석 |
| **실행 시점** | 상황 이벤트 발생, 구독한 서비스에 제한적으로 전달 | 이벤트에 대한 업무 로직 실행 |
| **결과 출력** | 허용된 카드·음성 형식, 표시 순서, 사용자 중단 | 결과 내용 생성 |
| **기록** | 무엇을 언제 누구에게 보냈고 무엇을 거절했는지 기록 | 자체 업무 처리 기록 |
| **에이전트 실행·기억** | 이번에는 필수가 아님. 권한 집행에 필요한 최소 상태만 보유 | 모델 선택, 추론 루프, 업무 메모리, 워크플로 |
| **운영 인프라** | 연동 규격과 정책 관리. 필요해지면 관리형 실행 추가 | 기존 서버·클라우드·AgentCore 등을 사용 가능 |

### 특히 세 가지는 플랫폼이 가져야 합니다

**첫째, 권한의 최종 결정권입니다.**  
매니페스트는 “이 서비스가 무엇을 원하는가”이지 “이 서비스에 무엇을 허용했는가”가 아닙니다. 선언과 승인 결과를 분리해야 합니다.

**둘째, 감각 데이터가 나가는 실제 경로입니다.**  
앱에 “이 함수를 사용해 주세요”라고 권하는 라이브러리만 제공하고 앱이 원본 카메라에도 직접 접근할 수 있다면, LensGate를 우회할 수 있습니다. AWS도 Gateway의 통제가 유효하려면 직접 호출로 우회할 수 없도록 구성해야 한다고 설명합니다. LensGate 역시 **우리 호스트가 관리하는 연결·세션 안에서 강제되는 경계**를 가져야 합니다. [AWS 문서](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html?utm_source=chatgpt.com)

**셋째, 사용자에게 결과를 내보내는 최소 규격입니다.**  
입력만 제공하면 개발자는 다시 글래스별 표시 코드를 작성해야 합니다. 따라서 “짧은 카드 표시”, “음성 한 문장”, “출력 취소” 정도는 공통 기능으로 제공하는 것이 좋겠습니다. 다만 이는 **LensGate가 관리하는 화면·오디오 경로의 조정**이지, 기기 전체의 모든 앱을 제어하는 OS 권한은 아닙니다.

반대로 **범용 에이전트 계획기, 장기 기억 시스템, 다중 에이전트 협업, 임의 코드 호스팅, 앱 마켓**까지 한 번에 소유할 필요는 없습니다.

## 5. 외부 서비스 방식으로 가면, 보장 범위는 반드시 달라집니다

여기는 중요합니다. **외부 API 연결 방식이 더 유연하다고 해서 현재의 모든 보장을 그대로 가져갈 수 있는 것은 아닙니다.**

현재 문서는 플러그인을 내부 Worker에서 실행하고, 그 실행환경의 네트워크 출구를 제한하는 구조입니다. 허용된 목적지 내부에서의 데이터 사용은 이미 비목표로 두고 있습니다. (출처: 02-SSRD, LensGate(가칭) PRD)

실행 방식을 넓히면 다음처럼 구분해야 합니다.

| 연결 방식 | LensGate가 통제할 수 있는 범위 | 통제한다고 말하면 안 되는 범위 |
|---|---|---|
| **LensGate 내부 실행 모듈** | 제공하는 입력, 해당 실행환경에서 허용되는 출구 | 허용된 외부 서버에 도착한 이후의 사용 |
| **외부 서버·에이전트 연결** | 제공하는 입력, 최초 수신처, 이후의 신규 접근 허용·철회 | 수신자가 이미 받은 정보를 복사·재전송·저장하는 행위 |
| **향후 관리형 실행 환경** | 우리가 운영하는 격리 환경 안의 입력·실행·출구 | 그 환경 밖으로 허용해서 내보낸 이후의 모든 사용 |

따라서 외부 서비스를 연결하는 모델의 약속은 이렇게 해야 합니다.

> **“이 서비스가 LensGate를 통해 받은 시각 데이터와 첫 전달 목적지를 확인할 수 있습니다.”**

다음과 같은 표현은 피해야 합니다.

> “이 서비스가 이후 어디에서도 이 데이터를 재사용하지 못합니다.”

권한 철회나 만료도 **앞으로의 접근을 막는 것**입니다. 이미 받은 이미지까지 원격으로 없애 주는 기능으로 설명해서는 안 됩니다.

이 차이를 받아들일 수 있다면 외부 서비스 연결형이 좋습니다. 반대로 고객 요구가 “외부 코드의 실행·네트워크·보관까지 우리가 통제해야 한다”라면, 그때는 관리형 런타임의 가치가 커집니다.

**즉, AgentOS로 갈지 여부는 ‘플랫폼처럼 보이는가’가 아니라 ‘고객이 실행환경까지 우리에게 맡겨야 하는가’로 결정하는 것이 맞습니다.**

## 6. 그래서 세 방향 중 무엇을 택하겠느냐면

### 범용 AgentOS: 지금은 추천하지 않습니다

이 방향을 선택하면 핵심 질문이 감각에서 멀어집니다.

어떤 에이전트 프레임워크를 지원할지, 프로세스를 어떻게 유지할지, 메모리를 어떻게 공유할지, 실패한 작업을 어떻게 재개할지, 모델 비용을 누가 부담할지까지 제품 책임이 커집니다.

이는 장기적으로 불가능해서가 아니라, **현재 LensGate의 고유한 문제를 해결하기 전에 범용 실행 인프라의 책임을 먼저 떠안기 때문**입니다.

### 단순 카메라 SDK: 이것만으로는 약합니다

카메라 연결과 앱 권한을 제공하는 기능 자체는 기존 플랫폼에도 있습니다. 예를 들어 MentraOS Cloud 문서에는 앱별 카메라·마이크 등의 권한 관리 API가 있습니다. 따라서 “SDK 하나로 카메라를 쓸 수 있다”만으로는 차별점을 설명하기 어렵습니다. [멘트라 클라우드 문서](https://cloud-docs.mentra.glass/api-reference/rest/permissions)

### 감각 접근·처리·출력을 묶은 런타임: 가장 추천합니다

개발자에게 주는 가치는 다음입니다.

> **기기 연결, 촬영 시점, 개인정보 처리, 입력 제한, 사용자 출력까지 매번 직접 만들지 않고, 자신의 서비스 로직에 집중할 수 있다.**

착용자에게 주는 가치는 다음입니다.

> **서비스마다 시야 전체를 열어 주지 않고, 필요한 순간에 필요한 정보만 제공하며 그 기록을 확인할 수 있다.**

이 둘이 같이 있어야 합니다. 프라이버시만 강조하면 개발자가 왜 붙여야 하는지 약하고, 개발 편의성만 강조하면 기존 SDK와 무엇이 다른지 약합니다.

단, **개발자가 실제로 이 중간 계층을 도입할지는 아직 검증해야 할 가설**입니다. 지금 문서만으로 플랫폼 수요까지 입증됐다고 보지는 않습니다.

## 7. 첨부한 HTML에 대한 의견

### 전체 평가

**내부 처리 흐름을 공유하는 자료로는 좋습니다. 하지만 개발의 최종 기준으로 바로 쓰기에는 명세 버전이 섞여 있습니다.**

특히 HTML은 “최신 ERD를 찾지 못했다”고 밝히고 있고, 실제로 현재 첨부된 SSRD·SRS·ERD와 다른 이름·순서·규칙을 사용합니다. 단순히 그림을 더 다듬기보다 **기준 문서를 고정하고 다시 대조하는 작업이 먼저**입니다. (출처: LensGate 유저플로우 SSRD판)

### 명세와 바로 맞춰야 하는 부분

| 항목 | HTML의 표현 | 현재 첨부 명세 기준 |
|---|---|---|
| 플러그인 준비 | `iframe → ready → boot` | `iframe load → init → Worker 준비 → ready → delivery` |
| 음식 우선 영역 | 중앙 50% | 중앙 60% |
| 기록 모델 | `DeliveryLog`, `PluginReportLog`, `RuntimeState` | `Delivery`, `LogEntry`, `Counter` 중심 |
| 같은 장면의 재전달 | 규칙이 없다고 보고, 새로 확정될 때만 전달 | 확정 장면이 유지되면 쿨다운 이후 다시 포착 |
| 빈도 제한 | 최근 60초 전달 수 검사 | SRS는 `60/maxPerMinute`의 포착 쿨다운 |
| API 라벨 | `label` 쿼리 | `x-label` 헤더 |
| 시작 버튼 | SSRD에 없다는 이유로 생략 | SRS에는 오디오 활성화를 위한 시작 버튼이 명시됨 |

메시지 순서·중앙 영역·라벨 전달 방식은 SSRD의 채택표에서 이미 구분되어 있고, 재전달은 SRS 상태 모델에 명시되어 있습니다. 로그 enum도 ERD에 존재합니다. (출처: 02-SSRD, 03-SRS, 04-ERD)

특히 **“분당 6번 이하”와 “10초마다 한 번 이하”는 같은 동작이 아닙니다.** 전자는 짧은 시간에 여러 번 보내는 것을 허용할 수 있고, 후자는 전달 간격을 고르게 제한합니다. 변경하려면 의도적인 정책 변경으로 결정해야 합니다.

### 가장 먼저 고칠 흐름: 전달 신호의 시점

HTML에서는 다음처럼 읽힙니다.

```text
사진 전달 → 서버 호출 → 결과 반환 → HUD·로그·전달 신호 갱신
```

실제로 결과 이후에 효과음·테두리 점멸을 배치하고 있습니다. (출처: LensGate 유저플로우 SSRD판)

추천은 다음입니다.

```text
사진을 실행환경으로 송신
→ 즉시 “전달됨” 신호
→ 수신 응답을 별도 표시
→ AI 처리 중
→ 결과 반환 시 결과 줄 갱신
```

**사용자가 알아야 하는 것은 ‘AI가 답한 순간’이 아니라 ‘자신의 정보가 넘어간 순간’입니다.** 응답이 실패하거나 지연돼도 정보 전달은 이미 일어났을 수 있기 때문입니다.

### HTML 마지막의 ‘팀이 정해야 할 것’에 대한 제 답

해당 다섯 가지 질문은 유용합니다. 다만 일부는 이미 명세에 답이 있고, 일부는 기존 결정 자체를 다시 검토해야 합니다. (출처: LensGate 유저플로우 SSRD판)

| 질문 | 제 의견 |
|---|---|
| 사람 장면에서 전달하지 않은 사실을 기록할까? | **기록하는 편이 좋습니다.** `LogEntry.kind=skip`, 사유 “미선언 장면”으로 표현할 수 있습니다. 반복 기록만 제한하면 됩니다. |
| 같은 장면이면 다시 보낼까? | 현재 SRS대로라면 **쿨다운 후 재포착**입니다. “규칙 없음”으로 새 결정을 만들 필요는 없습니다. |
| 스냅샷에서 대상을 놓치면? | **보류에 동의합니다.** 원본 전체나 이전 박스를 대신 보내지 말고, `hold`, `branch=null`, “대상 재검출 실패”로 남기는 안이 적절합니다. |
| 비교 모드를 끄면 M을 즉시 0으로 만들까? | **추천하지 않습니다.** 현재 보호 상태와 최근 전달 이력을 분리하세요. 모드 변경이 과거 전달을 없애지는 않습니다. |
| 비교 모드에서는 서버를 호출하지 않고 고정표를 쓸까? | **동의합니다.** 의도적으로 통신을 금지한 상태를 오류처럼 만들 필요는 없습니다. 단, 실행환경 교체가 끝난 뒤 비교 데이터 전달을 시작해야 합니다. |

또한 “초록 = 얼굴이 넘어가지 않음”, “보이는 얼굴 0개” 같은 문구는 측정 결과보다 강합니다. 사용 중인 얼굴 검출기가 반환하는 것은 얼굴 검출 결과·위치·신뢰도이지, 그 이미지로 사람을 알아볼 수 없다는 보증이 아닙니다. **“보호 처리 적용”, “전달본 얼굴 재검출 0개”처럼 정책 상태와 검사 결과를 구분하는 편이 정확합니다.** (출처: LensGate 유저플로우 SSRD판) [Google for Developers](https://developers.google.com/edge/mediapipe/solutions/vision/face_detector/python?utm_source=chatgpt.com)

### 더 근본적으로, 세 가지 사용자 흐름으로 나누면 좋겠습니다

지금 그림에서는 호스트가 하는 일이 대부분입니다. 플랫폼을 설명하려면 사람별로 다음 흐름이 보여야 합니다.

**개발자 흐름**

> 서비스 연결 → 필요한 감각 능력 선언 → 테스트 입력으로 검증 → 허용된 세션에서 수신 → 결과 반환 → 거부·전달 기록 확인

**착용자 흐름**

> 사용할 기능 선택 → 데이터 제공 범위 확인 → 세션 시작 → 자동 동작 → 전달 확인 → 일시 정지·권한 해제

**찍히는 사람을 위한 표시 흐름**

> 보호 정책·현재 동작 상태 확인 → 어떤 세션의 표시인지 확인 → 연결이 끊기면 ‘확인 불가’ 표시

특히 착용자 흐름에 **일시 정지와 권한 해제**가 보여야 합니다. 개발자가 JSON을 고치는 장면은 개발자 도구의 흐름이지, 일반 사용자의 권한 관리 경험을 대신하지는 못합니다.

## 8. 지금 만든 것을 버리지 않고 바꾸려면

여기서 당장 원격 API 플랫폼을 새로 구현하자는 뜻은 아닙니다. **이번 해커톤에서는 현재 Worker 구현을 유지하고, 제품 계약을 그 위로 한 단계 올리는 것**이 좋겠습니다.

### 이번 구현에서 유지할 것

입력 어댑터, 포착·가림·전달 경로, 권한 검사, 전달 로그, 내부 Worker 격리는 그대로 유용합니다. 현재 SRS도 이 경로를 중심으로 구성되어 있습니다. (출처: 03-SRS)

### 이번에 정리할 것

**외부 기능과 플랫폼 사이의 계약을 먼저 고정하세요.**

- 기능은 어떤 상황·정보를 요청하는가?
- 누가 실제 권한을 승인하는가?
- 플랫폼은 어떤 형태의 입력을 제공하는가?
- 기능은 어떤 결과 형식만 반환할 수 있는가?
- 중단·권한 변경 시 진행 중인 처리는 어떻게 취소하는가?

여기서 내부 Worker는 첫 번째 연결 방식입니다. 원격 서버 연결은 이후 같은 계약을 구현하는 두 번째 방식으로 추가할 수 있습니다.

이를 위해 지금 `Plugin`이라는 모든 타입과 파일명을 급하게 바꿀 필요도 없습니다. 대신 문서에 다음을 분명히 쓰는 것이 좋습니다.

> **현재 데모는 연결된 서비스를 내부 Worker에서 실행한다. 이는 참조 실행 방식이며, 장기적으로 외부 서비스 연결도 같은 감각 접근 계약을 사용한다.**

단, 원격 연결을 아직 구현하지 않았다면 발표에서는 **확장 설계**라고 해야지 현재 지원 기능처럼 말해서는 안 됩니다.

### 플랫폼성을 보여 주는 데모도 달라집니다

단순히 “JSON을 고치면 칼로리 기능이 달라진다”를 넘어서,

> **동일한 감각 런타임에 다른 수신 기능을 연결해도, 입력 제한과 기록 방식은 바뀌지 않는다.**

이 사실을 보여 주는 것이 더 중요합니다.

새로운 대형 앱을 만들 필요는 없습니다. 같은 규격의 관찰 데이터를 받는 간단한 두 번째 소비자나 테스트 클라이언트로도 **코어가 특정 칼로리 기능에 하드코딩되지 않았다는 것**을 검증할 수 있습니다.

## 최종 판단

**사용자님이 말한 API 기반 플랫폼 방향에는 찬성합니다. 다만 ‘API를 제공한다’에서 곧바로 ‘모든 에이전트를 우리 안에서 실행한다’로 넘어갈 필요는 없습니다.**

제가 선택할 순서는 다음입니다.

**감각 접근 계약과 로컬 런타임 → 외부 서비스 연결 → 필요가 확인되면 관리형 실행 환경.**

AgentOS는 그 뒤의 선택지입니다. 지금부터 AgentOS라는 이름을 붙이면 개발 범위뿐 아니라 고객에게 설명해야 할 책임까지 불필요하게 커질 수 있습니다.

PRD의 첫 문장은 이렇게 바꾸는 것을 추천합니다.

> **LensGate는 스마트글래스의 감각 정보를 외부 앱·에이전트가 제한된 권한으로 사용하도록 연결하는 런타임이다. 서비스의 실행 위치와 관계없이, 허용된 정보의 생성·전달·기록과 사용자 출력을 공통으로 관리한다. 이번 데모는 웹 입력과 내부 Worker 연결 방식으로 이 계약을 검증한다.**

핵심은 **“에이전트를 우리 플랫폼에 살게 하는 것”이 아니라, “어디서 실행되는 서비스든 사용자의 감각에 함부로 접근하지 못하게 하면서 쉽게 연결되게 하는 것”**입니다.
