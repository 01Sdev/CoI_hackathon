# famelet PRD: 1인칭 시각 데이터 중개 런타임

Oct 31, 2026 · @Kim.

## 개요

famelet은 1인칭 카메라와 그 위에서 도는 앱(플러그인) 사이에 끼워 넣는 **기기 중립 웹 런타임**이다. 앱은 원본 프레임 대신 목적에 필요한 조각 한 장만 받고, 착용자는 그 사실을 로그로 직접 확인하며, 찍힌 사람의 얼굴은 가려진 채로만 넘어가고, 위치가 불확실하면 아예 넘어가지 않는다.

- **해커톤:** INTHON, 마감 2026-11-01 12:00 KST, 3\~4명, 실작업 11\~16시간
- **산출물:** 심사위원이 배포 URL(또는 QR)로 노트북·휴대폰에서 직접 돌려 보는 웹 앱과 코드 저장소(레포). 레포에는 API 키 같은 비밀값을 넣지 않는다
- **한 문장 피치:** "카메라 앱이 무엇을 가져갔는지, 눈으로 확인할 수 있게 한다."

## 문제 정의

전제는 하나다. **기계에게 상시로 떠 있을 수 있는 눈이 생겼다.** 글래스·바디카·펜던트·휴대폰의 1인칭 카메라는 세션이 켜져 있는 동안 착용자의 시야를 그대로 앱에 넘긴다. 이 기계의 시각은 두 사람에게 문제를 만든다. 그 눈을 달고 다니는 착용자(문제 1)와 그 눈에 비치는 다른 사람(문제 2)이다. 기기 파편화(문제 3)는 이 둘을 해결하려 할 때 따라오는 추가 문제다.

### 1. 착용자 프라이버시: 앱은 필요한 것보다 훨씬 많이 본다

- 칼로리 앱에 필요한 건 접시 하나지만, 앱은 프레임 전체를 받는다. 그 안에는 집 내부, 모니터 화면, 문서, 위치 단서, 함께 있는 사람이 담긴다. 결제하려고 카드를 보는 순간에는 카드번호까지 넘어간다. 착용자는 그 사실을 알 방법이 없다.
- 휴대폰 카메라는 내가 들어 올릴 때만 찍히지만, 글래스는 세션이 켜져 있는 동안 시야 전체를 연속으로 넘긴다. Meta 글래스 기준 최대 720×1280·30fps이고, 공식 문서에 세션 시간 제한은 명시돼 있지 않다. 세션은 착용자가 글래스를 탭하거나, 벗거나, 다리를 접을 때 멈춘다.
- 권한은 앱 단위로 처음 한 번만 묻는다. "항상 허용"을 고르면 다시 묻지 않는다. Meta는 외부 앱으로 간 영상에 접근하지 않는다고 밝히는데, 이는 앱이 받은 프레임을 무엇에 쓰는지 중간에서 확인하는 주체가 없다는 뜻이기도 하다.

### 2. 찍힌 사람(제3자)의 초상권: 동의할 기회조차 없다

- 착용자는 앱을 고를 수라도 있지만, 카메라 앞을 지나간 사람은 자기 얼굴이 어느 서버로 갔는지 알 수도, 거부할 수도 없다.
- 얼굴 이미지는 개인을 알아볼 수 있는 개인정보다. 한국은 2023-09-15 시행된 개인정보보호법 제25조의2로 신체 착용형을 포함한 이동형 영상정보처리기기의 업무 목적 촬영을 제한하고, 불빛·소리·안내판 등으로 촬영 사실을 표시하도록 한다 ([서울시 안내](https://news.seoul.go.kr/gov/archives/554433), [제75조 과태료](https://www.itwiki.kr/w/%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4_%EB%B3%B4%ED%98%B8%EB%B2%95_%EC%A0%9C75%EC%A1%B0)).
- 촬영 사실 표시는 "찍히고 있다"만 알려 주고, "내 얼굴이 앱에 넘어갔는가"는 여전히 아무도 모른다.

**실제 사례:** 2024년 하버드 학생 두 명이 Ray-Ban Meta 글래스 영상에 얼굴 검색 서비스를 연결해 낯선 사람의 이름·주소·전화번호를 찾아내는 "I-XRAY"를 시연했다 ([404 Media](https://www.404media.co/someone-put-facial-recognition-tech-onto-metas-smart-glasses-to-instantly-dox-strangers)). 당시에는 인스타그램 라이브 스트림을 가로채는 방식이었고, 지금은 외부 앱이 SDK로 프레임을 직접 받는다.

### 3. 기기 파편화: 보장도, 앱도 기기마다 다시 만든다

- 글래스 제조사마다 SDK와 권한 모델이 다르다. Meta Wearables Device Access Toolkit은 iOS·Android 네이티브 전용이고, Ray-Ban Display 웹앱은 또 다른 규격이다.
- ~~글래스만의 문제가 아니다. 바디카·AI 펜던트 같은 웨어러블, 휴대폰 후면 카메라, 노트북 웹캠도 같은 1인칭 시각 데이터를 만든다.~~
- 그 결과 프라이버시 보장은 제조사 몫이 되고, 같은 앱도 기기마다 새로 만들어야 한다. 보장을 기기 아래가 아니라 **기기와 앱 사이 공통 계층**에 두어야 한다.

### 기존 시도의 한계

| 시도 | 하는 것 | 없는 것 |
| --- | --- | --- |
| MentraOS 매니페스트 권한 | 앱이 쓸 권한을 미리 선언 | 실제로 넘어간 데이터를 보여 주는 수단 |
| ContinuumXR 데이터 축소 계층 | 원본을 줄여서 전달 | 착용자가 확인하는 증명 |
| LensCap 등 연구 | 카메라 데이터 분리 설계 | 제3자 얼굴 보호, 기기 중립 런타임 |

공통점(우리가 확인한 범위): 줄여서 넘기는 데까지는 하지만, **넘어간 것을 사용자가 직접 확인하는 수단**은 중심에 두지 않는다. famelet의 차별점은 여기다.

### 왜 지금인가

- 2026년 5월 Meta가 Ray-Ban Display를 외부 개발자에게 열면서, 서드파티 글래스 앱 생태계가 만들어지기 시작했다.
- 생태계 초기에 규약이 정해지지 않으면, 휴대폰 앱처럼 "일단 다 가져가는" 관행이 굳는다.

## 대상 사용자

세 부류가 같은 화면을 다른 이유로 본다. 데모에서는 심사위원이 착용자와 찍힌 사람 역할을 동시에 체험한다.

| 사용자 | 상황 | 핵심 니즈 | famelet이 주는 것 |
| --- | --- | --- | --- |
| 착용자 | 글래스·휴대폰으로 AI 앱을 쓴다 | 앱이 내 시야를 어디까지 가져갔는지 알고 싶다 | 앱별 증명 로그, HUD의 "앱에 반영된 사람 수" |
| 찍힌 사람(제3자) | 누군가의 카메라 앞에 있다 | 내 얼굴이 내 동의 없이 앱에 넘어가지 않길 원한다 | 얼굴 가림, 불확실하면 전달 보류, 바깥 표시 화면 |
| 플러그인 개발자 | 글래스 앱을 만든다 | 기기마다 다시 만들기 싫고, 글래스 없이도 테스트하고 싶다 | 매니페스트 한 장 + 입력 어댑터, 웹캠·녹화 영상으로 개발 |

장기 구매자는 업무용 웨어러블을 도입하는 기업(현장 점검, 병원, 물류)이다. 이들은 이동형 영상정보처리기기 규정을 지켜야 하므로, "앱에 넘어간 것을 증명하는 로그"가 규제 대응 근거가 된다. 이 부분은 피칭용 방향이며 검증되지 않았다.

## 제품이 지키는 보장과 목표

다섯 가지 보장이 제품의 전부다. 기능을 빼더라도 이 다섯은 데모에서 진짜로 동작해야 한다.

1. **원본 비유출:** 원본 프레임과 가리기 전 조각은 휴대폰(웹 데모에서는 브라우저) 밖으로 나가지 않는다. 판정과 가림은 모두 로컬 모델로 하고, 서버는 이미 가린 조각만 받을 수 있다.
2. **최소 전달:** 플러그인은 매니페스트가 선언한 장면에서, 선언한 영역만, 선언한 해상도·빈도 이하로 받는다.
3. **격리와 출구 통제:** 플러그인 코드는 sandbox iframe 안의 Web Worker에서 돈다. 카메라·호스트 화면·원본에 닿을 수 없고, 네트워크는 매니페스트가 요청하고 호스트가 허용한 주소로만 나간다.
4. **제3자 보호 (불확실하면 차단):** 사람과 겹친 조각은 얼굴을 가린다. 얼굴 위치가 확실하지 않으면 머리 영역을 넓게 가리거나 아예 보내지 않는다.
5. **입력 완전성:** famelet이 플러그인에 전달한 카메라 데이터는 증명 로그에 있는 것이 전부다. 플러그인이 허용된 서버에서 받은 응답은 이 로그의 범위 밖이다. 근거는 경로가 하나뿐이라는 점(격리 + 중개기 단일 경로)이고, 로그의 숫자는 중개기가 실제로 보낸 파일에서 계산한다. 해시는 전송 무결성 확인용이며 보장의 근거로 내세우지 않는다.

**목표**

- 심사위원이 배포 URL 하나로, 별도 설치 없이 판정, 중개, 전달, 확인으로 이어지는 흐름을 3분 안에 직접 재현한다.
- 같은 플러그인이 웹캠, 휴대폰 후면 카메라, 녹화 1인칭 영상에서 코드 수정 없이 동작한다.
- 매니페스트 몇 줄 변경이 전달 데이터와 로그에 즉시 반영되는 것을 보여 준다.

**비목표 (이번 해커톤에서 하지 않는 것)**

- 실제 글래스 실시간 연결, 아이폰 중계, iOS 네이티브 앱 배포
- 3단계(기업 서버 재검사)의 실제 구현. 비활성 "미구현" 안내만 둔다
- 이미 넘어간 데이터의 회수. 권한 철회는 앞으로의 접근만 막는다
- 원격 서비스·에이전트 연결. 같은 계약을 브라우저 밖의 서비스에도 적용하는 것은 확장 설계로 발표에서만 다룬다
- 동의 등록과 인물 인식. 얼굴 특징값을 저장하는 순간 제품이 스스로 생체정보를 다루게 되므로 하지 않는다
- 플러그인 간 연동, 이벤트 버스, "걷는 중" 같은 추가 장면
- 시선 추적 ("시선" 대신 "화면 중앙"으로 표현)
- 플러그인 스토어, 승인 카드, 매니페스트 화면에서 새 플러그인 만들기
- 허용된 목적지에서 조각이 어떻게 쓰이는지의 통제. 범위는 "무엇을 받았는가"와 "어디로 나갈 수 있는가"까지다

## 처리 파이프라인

평소에는 거칠게 자주 보고, 필요할 때만 정밀하게 한 번 본다. 얼굴 검출은 매 프레임이 아니라 전달 직전의 조각에만 돌리고, 어려운 경우는 정밀하게 찾는 대신 넓게 가린다.

&#91;embedded content: 처리 파이프라인 · 4단계, 분기 2a\~2d\]

| 단계 | 실제 글래스 구성에서의 위치 | 웹 데모 구현 | 실행 빈도 |
| --- | --- | --- | --- |
| 0 훑어보기 | 글래스는 360×640·2\~7fps로만 송출, 판정은 휴대폰 | 입력 영상을 360×640으로 줄여 5fps로 EfficientDet-Lite0 실행 | 상시 |
| 1 포착 | 글래스 단일 프레임 캡처 → 휴대폰 | 같은 `<video>`에서 원본 해상도 프레임 1장 | 장면당 1회, 이후 `60 / maxPerMinute`초 간격 |
| 2 가림·분기 | 휴대폰 | 포착한 프레임에서 대상·사람을 다시 검출하고, `maxSide` 축소 전의 조각에 BlazeFace를 돌려 2a\~2d로 처리한 뒤 축소·JPEG 인코딩, 마지막에 출구 재검사 | 전달당 1회 |
| 3 확장 | 기업 자체 서버 (선택) | 구현 안 함. 비활성 "미구현" 안내와 "원본 서버 전송 0건" 표시만 | 기본 꺼짐 |

**2단계 순서**

1. 포착한 원본 프레임에서 대상과 사람을 다시 검출한다. 0단계 결과는 5fps라 포착 순간과 시점이 어긋나기 때문이다. 대상을 놓치면 보류한다.
2. `maxSide`로 줄이기 전의 조각에서 얼굴을 찾는다. 작게 줄인 뒤에는 얼굴을 놓치기 쉽다.
3. 사람 박스마다 대응되는 얼굴이 있는지 따로 판단한다. 검출된 얼굴은 모두 가리고, 얼굴이 대응되지 않은 사람에게는 2c·2d를 적용한다. 한 사람이라도 2d 조건이거나 대응이 불확실하면 조각 전체를 보류한다.
4. 안전 검사에는 장면 선택용 기준(화면 가운데 60%, 사람은 프레임 면적 5% 이상)을 쓰지 않는다. 멀리 있는 작은 사람도 검사 대상이다.
5. `maxSide` 이하로 줄여 JPEG로 만든 뒤 얼굴을 한 번 더 센다(출구 재검사). 보호 모드에서 1개 이상이거나 검사가 실패하면 보내지 않는다. 같은 모델로 다시 보는 것이라 가림 단계의 실수를 찾는 장치이지, 처음에 놓친 얼굴을 독립적으로 찾는 장치는 아니다.

**분기 기준값** (리허설로 튜닝)

| 기준 | 값 |
| --- | --- |
| 그대로 전달(2a) | 조각과 겹치는 사람도, 검출된 얼굴도 없음 |
| 사람과 겹침 | 사람 박스와 조각의 교집합이 조각 면적의 5% 초과 |
| 얼굴 재검출 | 조각 긴 변이 256px 미만이면 256px로 확대 후 BlazeFace, 신뢰도 0.5 |
| 얼굴 가림(2b) | 얼굴 박스를 15% 넓혀 6×6 픽셀화 |
| 넓게 가림(2c) | 사람 박스 위쪽 40%, 좌우 10% 여유 |
| 보류(2d) | 얼굴 미검출이면서 사람 박스가 조각 면적의 50% 이상 |

- **배터리:** 비용의 대부분은 고해상도 연속 전송과 매 프레임 처리다. BlazeFace 자체는 플래그십 기기에서 초당 200\~1000프레임 이상 돈다 ([BlazeFace](https://research.google/pubs/blazeface-sub-millisecond-neural-face-detection-on-mobile-gpus/)). 웹에서는 배터리를 재지 못하므로 처리량 패널(F16)의 모델 호출 횟수로만 말한다.
- **클라우드 원칙:** 원본이나 가리기 전 조각은 어떤 서버로도 보내지 않는다. 가리려고 클라우드에 보내면 가리기 전 얼굴이 그 서버로 가기 때문이다. 3단계는 이미 가린 조각만, 사용자가 켰을 때, 기업이 운영하는 서버로만 간다.
- **기기 중립:** 파이프라인은 같고 단계가 실행되는 위치만 기기에 따라 바뀐다. Meta 글래스는 외부 코드를 글래스에서 돌리지 않으므로 0단계 송출만 글래스가 하고, 코드를 실행할 수 있는 기기라면 0\~2단계가 기기 쪽으로 옮겨 간다. Meta 스트림은 처음부터 2·7fps를 고를 수 있지만, 대역폭이 부족해 자동으로 낮출 때는 15fps 아래로 내려가지 않는다. 발표 그림에서는 두 경우를 섞지 않는다.
- **웹 데모의 한계:** 휴대폰 한 대가 카메라이자 처리 장치라 단계가 물리적으로 나뉘지 않는다. 로그에 "처리 위치"를 표시하고, 실제 구성은 발표 그림으로 보여 준다.

## HUD·화면 요구사항

글래스 HUD의 주인공은 \*\*"현재 앱에 반영된 사람 수: 0명"\*\*이다. 제3자 보호라는 보장을 숫자 하나로 바꾸어, 착용자와 앞사람이 한눈에 확인하게 한다.

&#91;embedded content: 글래스 HUD 레이아웃 · 600×600, 요소 5개\]

**카운터 정의**

| 표시 | 정의 | 계산 위치 |
| --- | --- | --- |
| 화면 속 사람 N명 | 0단계 사람 검출(5fps)로 센 사람 수 | 판정기 (로컬, 밖으로 안 나감) |
| 현재 앱에 반영된 사람 수 M명 | 최근 10초 동안 실제로 보낸 전달물에서 출구 재검사가 잰 얼굴 수의 최댓값. 보호 모드에서 1 이상인 조각은 보내지 않으므로 평소에는 0이고, 비교 모드(F17)에서만 1 이상이 된다. 검사가 실패한 조각은 0으로 세지 않고 보내지 않는다 | 중개기 (실제 전달물 기준) |
| 세션 누적 | 앱별로 지금까지 얼굴이 담긴 전달 N건. 인물 식별을 하지 않으므로 서로 다른 사람 수는 세지 않는다 | 중개기 (화면 로그와 별개인 숫자 기록) |

- M은 판정기가 아니라 **중개기가 실제로 보낸 파일**에서 센다. 표시값이 곧 측정 결과가 되도록 하기 위해서다. 0은 현재 검출기로 잰 결과이며, 모든 얼굴이 없다는 보장은 아니다.
- 얼굴이 가려진 채 실렸거나 몸의 일부만 들어간 경우는 반영으로 세지 않는다. 기준은 "가리지 않은 얼굴이 검출되는가"다.
- 카운터는 화면 로그(최근 100건)와 따로 센다. 로그가 밀려나도 숫자는 줄지 않는다.
- M = 0이면 초록, M ≥ 1이면 주황으로 바뀌고, 어떤 전달물이 어느 앱에 넘어갔는지 보여 주는 확인 화면으로 이어진다.

**화면 모드.** HUD는 하나의 컴포넌트이고, 출력 기기마다 배치만 바뀐다. 입력뿐 아니라 출력도 기기 중립이다.

| 모드 | 기기 | 배치 |
| --- | --- | --- |
| 휴대폰 | 심사위원 폰 | 후면 카메라 전체 화면 + 가운데 600×600 HUD 오버레이, 하단 시트에 증명 로그 |
| 데스크톱 | 발표용 노트북 | 왼쪽 카메라+HUD, 오른쪽 탭(로그 / 확인 화면 / 매니페스트 / 처리량 패널) |
| 글래스 | `/hud` 경로 | HUD만 단독, 검은 배경, D-pad 조작(좌우는 최근 전달물 선택, 선택은 그 전달물 상세, 뒤로는 닫기). 입력은 녹화 영상(글래스 웹앱은 카메라를 쓸 수 없음). Ray-Ban Display 웹앱 시뮬레이터에서 열 수 있게 만든다 |
| 바깥 표시 | `/outward` 경로 | 찍히는 사람을 향한 화면. "지금 당신의 얼굴을 본 앱: N개"를 화면 높이 30% 이상 크기로. 같은 브라우저의 다른 창과 `BroadcastChannel`로 동기화하고, 0이면 초록, 1 이상이면 주황 |

**HUD 작성 규칙**

- 검은 배경(가산형 디스플레이에서 투명), 밝은 글자, 한 화면 요소 5개 이내
- 본문 24px 이상, 카운터 40px 이상 (600×600 기준)
- 색은 의미에만 쓴다: 초록 = 아무도 넘어가지 않음, 주황 = 비교 모드(상단 띠와 카운터), 빨강 = 차단 이벤트(변조 플러그인)
- 전달 신호(F9): 전달 순간 테두리가 300ms 밝아지고 "전달됨"이 뜨는 것이 기본이고, 효과음은 보조다. 보류(2d)는 소리 없이 하단 줄에 "보류"만 표시

## 진짜 구현과 목업의 경계

원칙은 하나다. **보장에 해당하는 부분은 전부 진짜, 플러그인이 내는 결과물 내용은 목업 허용.** 심사가 보는 건 칼로리 정확도가 아니라 "무엇이 넘어갔는가"다.

## 3분 데모 시나리오

다섯 가지 보장을 하나씩 눈으로 보여 주는 순서다. 발표자는 노트북(데스크톱 모드)을 화면에 띄우고, 심사위원은 QR로 자기 폰에서 따라한다.

1. **0:00–0:25 문제 (비교 모드):** 비교 모드를 켜고 팀원이 찍힌 녹화 영상으로 피자 장면을 튼다. 칼로리 앱이 원본 전체를 받고(통신은 막혀 있어 서버로는 가지 않음), HUD 카운터는 주황 "2명", 바깥 화면은 "당신의 얼굴을 본 앱: 1개". "기계에게 눈이 생겼고, 지금 이 앱은 여러분까지 봤습니다."
2. **0:25–0:45 접속:** 비교 모드를 끄고(보호 표시는 즉시, 카운터는 10초 안에 0), 심사위원이 QR로 자기 폰에서 연다. 후면 카메라 + HUD "현재 앱에 반영된 사람 수: 0명".
3. **0:45–1:10 최소 전달:** 피자를 비추면 효과음과 함께 조각 1장이 전달되고 칼로리 한 줄이 뜬다. 로그에 썸네일·바이트·원본 대비 비율·분기 2a.
4. **1:10–1:40 제3자 보호:** 피자를 얼굴 앞에 들면 2b(얼굴만 가림). 얼굴을 옆으로 돌리면 2c(머리 영역 넓게 가림). 사람만 비추면 "사람 앞 → 전달 0건"(로그에 "선언하지 않은 장면"). 바깥 화면은 계속 0개.
5. **1:40–2:05 격리:** 변조 플러그인을 켜면 네 가지 시도가 모두 "차단됨". 네트워크 탭에서 나간 요청은 조각 1장뿐이고 서버가 받은 바이트가 로그 바이트와 같음을 보여 주고, 매니페스트에서 칼로리 도메인을 지우면 그 호출도 막힌다.
6. **2:05–2:25 매니페스트:** `maxSide`를 256에서 64로 바꾸면 다음 전달부터 바이트가 줄어든다.
7. **2:25–2:45 기기 중립·처리량:** 입력을 녹화 1인칭 영상으로 바꿔도 같은 플러그인이 돈다. 처리량 패널에서 매 프레임 처리 대비 모델 호출 횟수를 보여 주고, 실제 글래스에서는 0단계 송출만 글래스, 1·2단계는 휴대폰이라는 그림을 띄운다.
8. **2:45–3:00 마무리:** "기계에게 눈이 생겼습니다. famelet은 그 눈이 무엇을 봤는지 사람이 알 수 있게 합니다."

## 리스크와 예상 질문

가장 큰 기술 리스크는 "얼굴을 놓치는 것"이고, 가장 큰 발표 리스크는 "런타임은 누가 검증하나"라는 질문이다.

| 리스크 | 조기 신호 | 대응 |
| --- | --- | --- |
| 얼굴 검출기가 옆얼굴·작은 얼굴을 놓침 | 리허설 썸네일에 선명한 얼굴 | 2c 넓게 가림 + 2d 보류. 사람 검출기까지 놓치는 경우만 남으므로 20회 실측치를 발표에서 말한다 |

| 1차 통합이 4\~5h에 안 붙음 | E2E 미완성 | 관문 규칙대로 P2를 모두 취소하고 A·B 트랙에 집중 |

**예상 질문과 답**

- **"런타임 자체는 누가 검증하나요?"** → 모두 브라우저 안에서 도는 오픈 코드다. 개발자도구 네트워크 탭에서 나가는 요청이 조각 1장뿐임을 누구나 확인할 수 있다. 신뢰 대상을 "모든 앱"에서 "런타임 하나"로 줄이는 것이 핵심이다.
- **"얼굴 검출이 놓치면요?"** → 사람 검출기가 몸을 잡으면 머리 영역을 넓게 가리고(2c), 판단이 서지 않으면 보내지 않는다(2d). 얼굴 검출은 가까운 얼굴을 정밀하게 가리고, 멀리 있는 사람은 사람 검출로 머리 영역을 넓게 가리도록 나눠 설계했다. 남는 위험은 두 검출기가 모두 놓친 얼굴 일부가 대상 조각 안에 들어오는 경우뿐이며, 리허설 실측치(20회 중 N회)를 발표 전에 채운다.
- **"해시가 일치하면 증명인가요?"** → 아니다. 해시는 전송 무결성만 보여 준다. 우리가 보장하는 것은 "famelet이 플러그인에 전달한 카메라 데이터는 로그가 전부"라는 입력 완전성이고, 그 근거는 격리와 단일 경로다. 해시는 기대값을 플러그인에 보내지 않고 호스트가 직접 대조하지만, 그래도 플러그인이 보내 온 값이라 독립된 수신 증명은 아니다.
- **"플러그인이 받은 조각을 밖으로 보내면요?"** → 매니페스트가 허용한 주소로만 나갈 수 있다. CSP가 못 막는 페이지 이동과 WebRTC는 Worker 실행으로 원천 차단했다. 허용된 목적지에서의 사용은 범위 밖이다.
- **"배터리는요?"** → 평소에는 저해상도·저프레임으로만 보고, 얼굴 검출은 전달 직전 조각에만 돌린다. 처리량 패널에서 매 프레임 처리 대비 모델 호출 횟수를 실측으로 보여 준다.
- **"보호를 끌 수 있다면 플러그인도 끌 수 있나요?"** → 아니다. 설정은 호스트 사용자(발표자 화면)만 바꾸고, 플러그인이 보호나 권한을 바꾸는 경로는 없다.
- **"실제 글래스에서도 되나요?"** → 이번에는 브라우저 입력 세 종류(웹캠·후면 카메라·녹화 영상)에서 같은 플러그인이 코드 수정 없이 도는 것까지 검증했다. 글래스 연결과 네이티브 중계는 아직 검증하지 않은 후속 과제다. Meta 글래스에서는 0단계 송출만 글래스가 하고 1·2단계는 휴대폰에서 돈다. Meta SDK는 네이티브 전용이라 다음 단계로 둔다.
- **"누가 플러그인을 올리나요?"** → famelet은 스토어가 아니라 플랫폼과 앱 사이의 계층이다. 탑재 주체는 글래스 플랫폼(권한 계층), 업무용 웨어러블을 도입하는 기업(규제 대응), 시각 보조 앱 개발사(신뢰가 곧 제품)다. 플러그인 개발자에게는 "한 번 만들면 웹캠·휴대폰·글래스에서 동작하고 장비 없이 개발한다"가 유인이다. 검증은 해커톤 이후 계획으로 제시한다.
